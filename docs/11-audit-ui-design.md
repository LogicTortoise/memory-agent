# 审计 UI 布局主题与交互

审计 UI 是个人检查记忆来源和处理过程的本地工具。用户要能回答：哪些 session 被扫描了、为何切成这些批次、模型看到了什么、某条要求怎样生成或更替、某次 query 为什么返回这些记忆。页面默认只读取元数据；展开原话与执行变更都由用户主动操作。

## 信息架构

| 导航 | 页面内容 | 主要操作 |
|---|---|---|
| 处理概览 | 扫描覆盖、四段处理计数、批次积压、失败与待决 | 扫描增量、处理队列、查看运行详情 |
| 会话与来源 | source 文件状态、generation、游标、session/branch、轮次 | 展开来源、定位未读区间、查看格式错误 |
| 处理批次 | 批次范围、输入 token、状态、尝试次数、产出与冲突数量 | 查看输入和候选、重试、取消未发布工作 |
| 记忆与决定 | 原子记忆、版本、范围、领域、证据和待决提案 | 对照版本、采用新要求、保留旧要求、补充范围 |
| 查询审计 | 原 query、改写/扩写、过滤、候选和排序轨迹 | 查看漂移、比较原 query 与扩写、展开引用 |
| 分类与系统 | 分类提案、运行配置概要、数据库/文件一致性、模型健康 | 查看影响范围、启动检查、查看需要用户处理的问题 |

关键路径是“概览→批次→原话/候选对照→记忆版本”，不是先展示一排无关的大数字。顶部只保留日期、数据更新时间和后台运行状态；统计直接嵌入扫描→规划→抽取→提交的流程条。

## 桌面布局

1440px 设计画布，左导航 208px，内容边距 28px。主要区域左对齐；正文阅读宽度限制约 680px，表格可横向延展。列表选中后出现右侧详情，批次深度检查使用独立双栏页。

```text
┌────────────┬──────────────────────────────────────────────────┐
│ Memory     │ 处理概览                  日期      后台运行状态  │
│            ├──────────────────────────────────────────────────┤
│ 处理概览   │ 扫描覆盖 → 已规划 → 已抽取 → 已提交              │
│ 会话来源   │ 需要处理：1 个源格式异常 / 2 项待确认             │
│ 处理批次   ├─────────────────────────────┬────────────────────┤
│ 记忆决定   │ 批次列表                    │ 选中批次摘要       │
│ 查询审计   │ session / 轮次 / token      │ 来源与输入范围     │
│ 分类系统   │ 执行状态 / 待决数           │ 最近动作与下一步   │
│            │                             │ 打开原话对照       │
└────────────┴─────────────────────────────┴────────────────────┘
```

批次详情：顶部面包屑与状态；左栏为 5 轮对话的顺序，右栏为抽取候选。点击候选原句引用时左栏定位到确切 message/span，高亮引用；点击左栏被省略工具输出可按需展开。底部“本批次处理范围”列明 target/context_only、截断、尚缺的上下文，不把 5 轮数量当成全部输入已读的保证。

冲突详情：旧要求和新候选并列，范围/有效时间单独一行，源引用可展开。操作区显示“采用新要求”“保留旧要求”“按范围并存”“稍后”；并存必须填写范围，提交前展示实际更改。页面加载后提案版本变了，禁用旧操作并要求重新读取，保留用户尚未提交的备注。

查询详情：上方原 query 固定可见；改写和扩写各一行，旁边显示保留/拒绝与原因；下方候选表展示原查询名次、扩写命中、BM25 分数、重排名次、最终采用与引用。默认不显示复杂公式，展开“排序依据”可检查参数与 tokenizer_version。

## 主题与视觉取舍

采用“对话证据工作台”的克制布局：浅冷灰底、深蓝文字、明确的处理路径和对照栏。重点视觉是原句与候选间的关联高亮；不用渐变背景、营销大标题、每一项都放相同卡片或无意义动画。

| token | 浅色主题 | 深色主题 | 用途 |
|---|---|---|---|
| canvas | #F5F7FA | #182230 | 页面底色 |
| surface | #FFFFFF | #223044 | 列表、正文、详情 |
| ink | #20304A | #E5EBF3 | 主要文本 |
| muted | #596A82 | #AFBDD0 | 次要说明与元信息 |
| line | #D6DEE8 | #46566D | 表格分隔与边框 |
| accent | #315D92 | #A6C9F5 | 选中、链接、焦点 |
| success | #246750 | #90D5BD | 已提交与检查通过 |
| pending | #89570C | #F2C778 | 待决定/待补上下文 |
| danger | #A0353C | #F4AFB4 | 失败或明确破坏性操作 |

默认跟随系统，允许固定浅色/深色。主题是 CSS custom properties，不在每个组件写独立颜色。状态使用图形/文字与颜色共同表达：“已提交”“待确认”“失败”不能只靠绿黄红区分。

中文使用系统 PingFang SC / Noto Sans CJK SC 回退，界面西文使用系统 sans-serif，不在线下载字体。原文保持易读常规字形；仅 ID、路径、游标偏移和代码使用系统等宽字体。标题 24px，正文 14–16px，次要信息不低于 12px，正文行高约 1.6。采用 4/8px 间距系统，表行 44–52px，长文本引用可折叠而不裁掉关键否定。

## 响应式与可访问性

≥1280px 使用导航+列表+详情；960–1279px 详情作为可关闭侧栏；<960px 以列表→详情单页导航代替三栏，原话/候选用标签页切换但保持引用定位。小屏优先检查和决定，不把大表格缩成不可读文字。

全部操作支持键盘、可见焦点、原生 button/input/table 语义；对话引用跳转后明确朗读定位。普通文字对比度目标至少 4.5:1，图形/交互边界至少 3:1；主题 token 要在对应背景验证。减少动画偏好下禁用滑动过渡，任务更新不抢焦点。

## 页面状态与行为

| 状态 | 页面表现 | 行为 |
|---|---|---|
| 首次未扫描 | 展示配置的 sources 和起始范围，无虚假“0 条处理成功” | 用户点扫描或等待日任务 |
| worker 离线 | 标出最后心跳与快照时间 | 仍可读取；提交异步命令明确显示排队 |
| 只有半条尾记录 | source 上显示“等待记录写完” | 不标失败、不推进该边界 |
| batch needs_context | 显示缺失指代和 source refs | 允许补充来源/稍后处理，不默认全局化 |
| 批次完成但有冲突 | 执行状态“已完成”，待决事项单独计数 | 继续后续批次，用户独立处理提案 |
| 发布待 finalize | 显示“内容已发布，状态对齐中” | 禁止重复发布，提供恢复诊断 |
| query 无结果 | 展示查找范围与已执行变体 | 用户可调整范围，不暗示记忆不存在 |
| 部分数据 | 明示未扫描/未重排/截断范围和分页 | 不显示虚假的完整百分比 |

浏览审计不调用模型。重试、重规划、手动查询、重新生成摘要等有成本动作通过 POST commands 创建 job，按钮说明影响的批次/对象；加载状态禁止重复发送，但后端仍必须幂等。普通查看和分页不需要反复确认。

## 审计数据绑定

UI 不自行计算处理状态。后端根据 SQLite 与文件 manifest 的已对齐状态生成 DTO；每个 DTO 带 as_of、snapshot_id、projection_state、分页 cursor。具体表与统计口径见 [状态与审计数据](12-state-and-audit-data.md)，请求契约见 [脚本和服务接口](10-script-and-service-api.md)。

OverviewDTO：sources coverage、new events/turns、planned/extracted/committed batches、oldest backlog、open conflicts、errors、worker heartbeat。BatchDTO：source/session、target units、context_only、policy、actual turn/token counts、attempt、status、candidate/commit refs、pending conflicts。EvidenceDTO：仅该批实际可见的原话、role、span、source locator、裁剪标记。QueryTraceDTO：original/variants/filters、候选路径与排名、重排变化、调用用量与分页覆盖。

AuditEventDTO 展示时间、执行者、动作、对象、原因、前后版本和来源跳转。模型提出的建议用“模型提案”标记，用户决定分别标为 CLI/UI/Telegram；不能把模型输出显示成用户已批准。

## 前后端技术选择

本地 FastAPI 提供审计只读查询和统一命令入口；React + TypeScript + Vite 构建静态 UI，随 Python 包/发行目录发布。使用原生表格与服务端分页、CSS 变量主题，首版不加入大型组件套件、实时消息中间件或独立前端云服务。选择理由是本地 API schema 可与 Pydantic 合同对齐，页面与后台业务保持清楚边界。

UI 只有 views/components/api client，不实现冲突判定、批次切分、SQL 写入或文件提交。HTTP 入口复用应用服务；模型 provider、SQLite 和文件路径都不暴露给浏览器自由操作。

## 静态设计稿与验收

[处理概览](../design/audit-overview-light.svg)、[批次原话对照](../design/audit-batch-detail.svg)、[深色主题概览](../design/audit-overview-dark.svg)是带虚构示例数据的静态设计稿，不是已开发 UI。

验收需要：从批次定位到原话 span；分清完成与待决；旧版本按钮不能提交；查询改写可追溯且原 query 始终可见；页面刷新不触发模型；恢复期间展示真实状态；键盘和窄屏可完成一次冲突处理；明暗主题对比度达标。真实数据脱敏、性能和交互自动化将在开发阶段检查。
