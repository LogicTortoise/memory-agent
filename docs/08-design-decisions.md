# Memory Agent 当前设计决策

以下是当前有效决策。早期方案中的 hook 主录入、全面禁止 BM25、运行状态全部写 JSON 的设计已经被用户后续要求替换；原始用户陈述与研究报告作为历史保留，不构成现行实现合同。

| ID | 当前选择 | 依据与代价 |
|---|---|---|
| D01 | 离线指后台异步，允许云模型 | 用户确认；最小上下文与 local_only 策略仍有效 |
| D02 | 自动读取本地 session 新增，Reader 标准化事件 | 用户明确要求扫描；私有格式变化需适配 fixture |
| D03 | SQLite 登记扫描游标和事件队列，原文存 segment 文件 | 避免细碎状态到处分散；文件/DB 边界需恢复协议 |
| D04 | 默认 5 轮一批，最多输入 token 同时限制，可调 10 轮 | 针对较弱离线模型；不足 5 轮不无限等待，长轮次拆片或澄清 |
| D05 | 标准化角色、目标/context_only、span 和来源 revision | 审计能看到模型实际读了什么，避免重叠/重放变成重复证据 |
| D06 | 原子记忆 Markdown，来源/提案/提交 JSON | 内容人可读可追溯，稳定 ID 不因分类移动 |
| D07 | 原则/细节与长期/短期、项目/领域等分面独立 | 不把高频自动升级全局，分类调整不扩大 scope |
| D08 | 无冲突提案可自动发布；不明/矛盾待用户决定 | 批次可完成但冲突未决，两种状态分开 |
| D09 | 日期、领域、项目、标签文本视图 | 导航透明，可重建；不能用摘要代替原子证据 |
| D10 | BM25 仅在显式 recall 时内存计算 | 用户最新允许；不用于捕获/批次/分类/冲突，不部署搜索服务 |
| D11 | 原 query 保留，1 个改写和最多 2 个扩写 | 变体不改变硬范围、数字/实体和否定；漂移可审计 |
| D12 | 独立 Python CLI + worker | 不依赖个人中控；系统服务仅托管进程 |
| D13 | 统一 CommandRequest/Response，sync/async、幂等和明确退出码 | 外部脚本直接使用，不要求 HTTP/Agent 会话常驻 |
| D14 | SQLite 存状态、lease、审计、用量、通知 | 数据库是运行状态权威，不能像派生索引一样随意删掉 |
| D15 | 文件发布使用 commit intent→HEAD→DB finalize | 不假装跨介质原子事务；崩溃后对齐再继续写 |
| D16 | 项目独立 Telegram bot 适配 | 接收器单实例，决定耐久保存后推进游标 |
| D17 | 本地 FastAPI + React/TypeScript/Vite 审计 UI | 原话/提案对照、查询 trace、状态与游标可查；浏览不调用模型 |
| D18 | 17 个开发工作包与明确目录拥有边界 | 每包输入/输出/验收可检查，接口变更集中管理 |
| D19 | 独立删除清单优先于旧文件/旧数据库 | 备份恢复先应用删除，缺失最新清单时不能假装可安全恢复 |
| D20 | 本轮仅设计、静态示意与文档验证 | 没有扫描真实 session、建运行 DB、写产品代码或部署 UI |

## 用户修订记录

2026-10-08 首次补充要求项目独立并排除 BM25；因此撤销外部中控依赖。随后用户进一步明确：采集以本地 session 增量扫描为主，默认约 5 轮小批处理，接口可由外部脚本调用；BM25 若仅用于查询可以采用，同时注意 query 改写/扩写。之后明确允许 SQLite 保存细碎状态，并要求审计 UI、开发工作包和代码目录设计。当前文档以这些最新要求为准。

## 开发前验证项

- Reader 对实际受支持 Claude Code/Codex 版本的消息/turn/branch/重放格式能否准确解释；本轮未读取真实会话验证。
- 5 轮与 token 双预算对所选小模型的抽取质量，跨批前文引用是否足够。
- 文件 segment→DB 游标以及 HEAD→SQL finalize 的全部崩溃窗口。
- query 扩写的增益与漂移率，BM25 的查询构建成本和中文覆盖。
- UI 的操作版本校验、隐私脱敏、明暗主题和真实数据分页表现。
- 独立 worker、系统托管、Telegram 接收和 SQLite 一致备份在实际部署环境的行为。

这些由开发阶段验收，不由本轮请求用户凭据、读取历史或运行未实现命令来冒充确认。
